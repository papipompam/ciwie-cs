# 1.3 ขอบเขตของระบบ

## ข้อกำหนดล่าสุด — Workflow สหกิจศึกษา (6 กันยายน 2569)

ข้อกำหนดส่วนนี้มีผลแทนข้อความเดิมที่ขัดกันด้านล่าง:

- นักศึกษาสมัครได้ครั้งละหนึ่งสถานประกอบการ โดยต้องระบุชื่อตำแหน่ง ชื่อและที่อยู่สถานประกอบการ รวมถึงพิกัดให้ครบถ้วน
- นักศึกษาสมัครสถานประกอบการใหม่ได้เมื่อสถานประกอบการก่อนหน้าปฏิเสธเท่านั้น การยกเลิกโดยนักศึกษาไม่ปลดล็อกสิทธิ์สมัครใหม่
- เมื่อนักศึกษายืนยันสถานประกอบการ ระบบส่งข้อมูลเข้าคิวคำร้องของเจ้าหน้าที่ทันที
- ระบบเสนอการจัดกลุ่มสถานประกอบการจากพิกัดด้วย hierarchical clustering โดยใช้ระยะเส้นตรงและจำนวนสูงสุดต่อกลุ่ม ไม่ใช่ระยะขับรถหรือบริการ LLM ภายนอก หลังได้กลุ่มแล้วเจ้าหน้าที่เป็นผู้เลือกอาจารย์เอง และอาจารย์ต้องไม่ซ้ำกลุ่มในรอบกับครั้งเดียวกัน
- อาจารย์หรือเจ้าหน้าที่สามารถทำแบบประเมินสถานประกอบการหนึ่งชุดต่อรายการนิเทศได้ โดยประเมินความเหมาะสมของงาน ผู้ดูแล สิ่งแวดล้อมและความปลอดภัย ทรัพยากร เบี้ยเลี้ยง การเดินทาง ที่พักใกล้เคียง และการประสานงาน พร้อม rating, review และข้อเสนอแนะ
- เจ้าหน้าที่ส่งออกผลคะแนนประเมินที่ส่งแล้วเป็น CSV หรือ XLSX ตามรอบ ครั้ง และตัวกรองทั้งหมดได้
- Dashboard เจ้าหน้าที่แสดงสัดส่วนนักศึกษาตามสถานะการได้สถานประกอบการในรูปแบบกราฟวงกลม
- เฉพาะเจ้าหน้าที่เท่านั้นที่ตรวจคำร้อง ตรวจหนังสือตอบรับ และออกหนังสือขอความอนุเคราะห์ อาจารย์ไม่มีสิทธิ์เข้าถึงคำร้องขอเอกสาร
- ส่วนนี้ยังเป็น UI prototype: กลุ่ม คำร้อง ผลประเมิน และสิทธิ์อยู่ใน session ฝั่งแอป ยังไม่ใช่ persistence หรือ RBAC ฝั่ง server สำหรับ production

> **สถานะเอกสาร:** ปรับจาก UI Prototype ที่มีอยู่จริง ณ วันที่ 1 กันยายน 2569
> โดยตรวจจาก route, หน้าจอ, component, validation, mock state และ interaction ในโค้ด
> หากข้อความเดิมขัดกับพฤติกรรมที่ทำได้จริง ให้ยึดข้อกำหนดและข้อจำกัดที่ระบุในเอกสารฉบับนี้

หลักการตีความขอบเขตมีดังนี้

-   Developer Scenario, การสลับบทบาท, mock account, mock file และข้อมูล seed
    ใช้สำหรับตรวจ UI เท่านั้น ไม่ใช่กลไกสิทธิ์หรือการจัดเก็บข้อมูลของระบบจริง
-   ขอบเขตที่ไม่มี route หรือ action รองรับใน Prototype ไม่ถือว่าเป็นความสามารถปัจจุบัน
    และต้องระบุเป็นงานส่งต่อ Backend หรือสิ่งที่อยู่นอกขอบเขตอย่างชัดเจน
-   ระบบแยก “รายการบริษัทที่นักศึกษาสมัคร” ซึ่งรับสมัครได้ครั้งละหนึ่งแห่ง
    ออกจาก “คำร้องข้อมูลที่ฝึกงาน” ซึ่งเป็นคำร้องทางการสำหรับออกหนังสือ
-   สถานที่ฝึกงานที่ยืนยันแล้วเป็นผลจากคำร้องและใช้ต่อในการจัดกลุ่มกับตารางนิเทศ
    โดยสถานะการปฏิบัติงานไม่เปลี่ยนอัตโนมัติตามวันที่ ตารางนิเทศ หรือผลประเมิน
-   หน้ารายการข้อมูลต้องยึด Loading, Empty, Error และ Data state รวมถึง Desktop table,
    Mobile card, filter, reset และ pagination ตาม Design System ที่ `/dev/ui`

## 1.3.1 ส่วนสำหรับเจ้าหน้าที่

-   สามารถเข้าสู่ระบบและออกจากระบบได้
-   สามารถเปิดใช้งาน ระงับ ยุติการใช้งาน และรีเซ็ตรหัสผ่าน
    ของบัญชีนักศึกษาและอาจารย์ได้
-   สามารถเพิ่ม แก้ไข สืบค้น และยุติการใช้งานข้อมูลนักศึกษาและข้อมูลอาจารย์
    โดยไม่ลบข้อมูลและประวัติที่เคยเกิดขึ้นจริงออกจากระบบ
-   สามารถนำเข้าและส่งออกข้อมูลนักศึกษาและอาจารย์ด้วยไฟล์ CSV หรือ Excel ได้
-   สามารถสร้างกลุ่มนิเทศและกำหนดอาจารย์ผู้รับผิดชอบของแต่ละกลุ่ม
    โดยแบ่งการนิเทศออกเป็นครั้งที่ 1 และครั้งที่ 2
-   สามารถเพิ่ม แก้ไข ค้นหา ดูรายละเอียด ยุติการใช้งาน
    และลบสถานประกอบการที่ยังไม่มีข้อมูลอ้างอิงได้
-   สามารถเปิดดูและแก้ไขข้อมูลนักศึกษาที่ฝึกอยู่ในสถานประกอบการแต่ละแห่งได้
-   สามารถดูและค้นหาประวัติการสมัครสหกิจของนักศึกษาทั้งหมด
    พร้อมกรองตามรุ่น หมู่เรียน ภาคเรียน สถานะการสมัคร และจังหวัดได้
-   สามารถตรวจคำร้อง แนบหนังสือขอความอนุเคราะห์ และตรวจหนังสือตอบรับได้
-   สามารถดู Dashboard ตามรอบ ปฏิทิน การแจ้งเตือน และความคืบหน้าการประเมิน
    ของรายการนิเทศทุกกลุ่มได้
-   หน้าตารางนิเทศของเจ้าหน้าที่ใช้ติดตามรายการ และทำแบบประเมินสถานประกอบการ
    หลังนิเทศเสร็จได้ แต่ไม่มี action สร้าง เผยแพร่ แก้ไข เลื่อน หรือยกเลิกรายการนัด

## 1.3.2 ส่วนสำหรับอาจารย์

-   สามารถเข้าสู่ระบบและออกจากระบบได้
-   สามารถเปลี่ยนรหัสผ่านของตนเองได้ และต้องเปลี่ยนรหัสผ่านก่อนเข้าใช้งานครั้งแรก

-   สามารถดูตารางการนิเทศที่ตนเองได้รับมอบหมาย โดยแสดงครั้งที่นิเทศ วันที่ ช่วงเวลา
    สถานประกอบการ และรายชื่อนักศึกษาที่ต้องไปนิเทศได้

-   สามารถเพิ่มหรือแก้ไขอาจารย์ผู้เข้าร่วมนิเทศในรายการที่ตนเองรับผิดชอบได้
    รวมถึงเข้าร่วมนิเทศกับกลุ่มอื่นเป็นบางรายการโดยยังคงอยู่ในกลุ่มรับผิดชอบเดิม

-   หน้า detail แสดงวันที่ ช่วงเวลา และรายชื่อผู้เข้าร่วมให้แก้ไขได้
    แต่ Prototype บันทึกค่าดังกล่าวพร้อมการยืนยัน “นิเทศเสร็จแล้ว” เท่านั้น
    ยังไม่มีปุ่มบันทึกตารางแยก การตรวจตารางชน หรือประวัติการเปลี่ยนตาราง

-   สามารถค้นหา ดูประวัติ และแก้ไขคำนำหน้า ชื่อ และนามสกุลของนักศึกษาได้
    โดยสิทธิ์นี้แยกจากงานตรวจคำร้องและเอกสาร ซึ่งอาจารย์ไม่มีสิทธิ์เข้าถึง
-   สามารถดูรายละเอียดสถานประกอบการที่เกี่ยวข้องกับการฝึกสหกิจศึกษาได้
-   สามารถเพิ่ม แก้ไข ค้นหา ดูรายละเอียด ยุติการใช้งาน
    และลบสถานประกอบการที่ยังไม่มีข้อมูลอ้างอิงได้
-   สามารถเปิดดูและแก้ไขข้อมูลนักศึกษาที่ฝึกอยู่ในสถานประกอบการแต่ละแห่งได้

-   สามารถค้นหาข้อมูลนักศึกษาโดยใช้รหัสนักศึกษา ชื่อ หรือนามสกุลได้

-   สามารถดูประวัติการสมัครสถานประกอบการของนักศึกษาแต่ละคน
    เพื่อทราบว่านักศึกษาได้สมัครสถานประกอบการใดบ้าง ตำแหน่งที่สมัคร วันที่สมัคร
    และสถานะปัจจุบันของการสมัคร

-   สามารถค้นหาและกรองข้อมูลนักศึกษาตามสถานประกอบการหรือสถานะการสมัคร
    เพื่อใช้ในการติดตามความคืบหน้าในการหาสถานที่ปฏิบัติงานสหกิจศึกษาได้

-   อาจารย์ไม่มีสิทธิ์เปิดดู ตรวจ ยืนยัน หรือส่งกลับคำร้องและเอกสาร งานทั้งหมดเป็นหน้าที่ของเจ้าหน้าที่

-   สามารถยืนยันรายการที่ตนอยู่ในกลุ่มรับผิดชอบหรือมีชื่อเข้าร่วม
    ให้เป็น “นิเทศเสร็จแล้ว” ได้ โดยระบุอาจารย์ที่เข้าร่วมจริงอย่างน้อย 1 คน
-   Prototype มีสถานะฉบับร่าง รอการนิเทศ เลื่อนนัด นิเทศเสร็จแล้ว และยกเลิก
    แต่ UI ยังไม่มี action สร้าง เผยแพร่ เลื่อน หรือยกเลิกรายการ

-   สามารถบันทึกผลการนิเทศ ปัญหาที่พบ ข้อเสนอแนะ
    และรายละเอียดที่เกี่ยวข้องกับนักศึกษาในการนิเทศแต่ละครั้งได้

-   สามารถบันทึกความต้องการของสถานประกอบการ (Requirement) ที่ได้รับจากการนิเทศ
    โดยระบบมีช่องข้อความสำหรับให้อาจารย์บันทึกรายละเอียดความต้องการ ข้อเสนอแนะ
    หรือข้อมูลเพิ่มเติมจากสถานประกอบการแยกจากผลการนิเทศ
    เพื่อใช้เป็นข้อมูลประกอบการติดตามและพัฒนาการดำเนินงานสหกิจศึกษา

-   อาจารย์ผู้เข้าร่วมนิเทศจริงทุกคนต้องประเมินนักศึกษาเป็นรายบุคคล
    หลังจากดำเนินการนิเทศในแต่ละครั้ง

-   แต่ละรายการนิเทศต้องมีแบบประเมินสถานประกอบการร่วมหนึ่งชุด
    โดยอาจารย์ผู้รับผิดชอบหรือเจ้าหน้าที่เป็นผู้จัดทำก็ได้ ผู้ส่งก่อนจะล็อกแบบประเมินชุดนั้น

## 1.3.3 ส่วนสำหรับนักศึกษา

-   สามารถเข้าสู่ระบบและออกจากระบบได้
-   สามารถเปลี่ยนรหัสผ่านของตนเองได้ และต้องเปลี่ยนรหัสผ่านก่อนเข้าใช้งานครั้งแรก

-   สามารถเพิ่ม แก้ไข และอัปเดตสถานะ “รายการบริษัทที่สมัคร” ได้ครั้งละหนึ่งแห่ง
    และสมัครแห่งใหม่ได้เฉพาะเมื่อบริษัทก่อนหน้าปฏิเสธ
-   สถานะรายการบริษัทที่สมัครประกอบด้วย ยื่นสมัครแล้ว รอการตอบกลับ
    บริษัทตอบกลับแล้ว รอสัมภาษณ์ ผ่านการสมัคร และปฏิเสธ

-   สามารถค้นหาและดูรายละเอียดข้อมูลสถานประกอบการได้

-   ต้องบันทึกชื่อตำแหน่ง ชื่อบริษัท ที่อยู่ จังหวัด และพิกัดของสถานประกอบการให้ครบ
    โดยข้อมูลผู้รับหนังสือและที่อยู่ออกหนังสือยังแยกจากที่อยู่สถานประกอบการ

-   Prototype อนุญาตให้มีรายการสมัครที่ยังดำเนินการอยู่ครั้งละหนึ่งบริษัท
    และปลดล็อกการสมัครใหม่เมื่อบริษัทเดิมปฏิเสธเท่านั้น

-   สามารถแก้ไขคำร้องของตนเองได้ก่อนถูกนำไปรวมในชุดหนังสือ
    ได้แก่สถานะฉบับร่าง ส่งแล้ว หรือถูกส่งกลับ ส่วนคำร้องที่รวมชุดแล้วถูกล็อก

-   สามารถบันทึกข้อมูลการสมัคร ได้แก่ สถานประกอบการ ตำแหน่งที่สมัคร วันที่สมัคร
    รายละเอียดที่เกี่ยวข้องแบบไม่บังคับ ชื่อผู้รับหนังสือ ตำแหน่งหรือหน่วยงานของผู้รับ
    และที่อยู่สำหรับออกหนังสือได้ โดยข้อมูลผู้รับหนังสือเป็นข้อมูลของคำร้องแต่ละครั้ง
    และไม่ถูกบันทึกเป็นข้อมูลหลักถาวรของสถานประกอบการ

-   สามารถดูรายการและประวัติคำร้องขอฝึกงานของตนเอง
    รวมถึงสถานะล่าสุดของคำร้องและชุดหนังสือแต่ละแห่งได้

-   สามารถยกเลิกคำร้องที่ยังไม่ถูกรวมในชุดหนังสือหรือยังไม่ได้ออกหนังสือได้
    ได้แก่สถานะฉบับร่าง ส่งแล้ว หรือถูกส่งกลับ ส่วนคำร้องที่เข้าชุดหรือออกหนังสือแล้วถูกล็อก
    และ Prototype ยังไม่มี flow ส่งคำขอยกเลิกให้อาจารย์

-   สามารถดูข้อมูลสถานประกอบการที่ได้รับการยืนยันเป็นสถานที่ปฏิบัติงานสหกิจศึกษาของตนเองได้

-   สามารถติดตามสถานะคำร้อง เหตุผลส่งกลับ และ timeline ของคำร้องได้
-   เมื่อนักศึกษายืนยันสถานประกอบการ ระบบแจ้งเจ้าหน้าที่และแสดงสถานะ
    “รอรับเอกสาร” ทั้งหน้าหลักและหน้าสมัคร โดยยังไม่แสดงลิงก์ดาวน์โหลด
    จนกว่าเจ้าหน้าที่จะอัปโหลดหนังสือขอความอนุเคราะห์
-   หลังได้รับหนังสือแล้ว นักศึกษาดาวน์โหลดไฟล์ แนบหนังสือตอบรับ PDF
    และกดส่งให้เจ้าหน้าที่ตรวจได้อย่างชัดเจน

-   สามารถดูผลการตรวจสอบและการยืนยันสถานที่ฝึกงานของตนเองเป็นรายบุคคลได้
    แม้จะใช้หนังสือขอฝึกงานและหนังสือตอบกลับร่วมกับนักศึกษาคนอื่น
-   สามารถดูสถานะการปฏิบัติงานของตนเองได้

-   สามารถดูตารางการนิเทศของตนเอง โดยแสดงครั้งที่นิเทศ วันที่ ช่วงเวลา
    สถานประกอบการ อาจารย์ผู้นิเทศ และสถานะการนิเทศได้
    รวมถึงดูรายชื่อเพื่อนที่ฝึกในสถานประกอบการเดียวกันและอยู่ในรายการนัดเดียวกัน
-   สามารถเปิดดูรายการแจ้งเตือนตัวอย่างเรื่องเอกสารและตารางนิเทศภายในระบบ
    โดย action ทางธุรกิจยังไม่สร้างรายการใหม่อัตโนมัติ
-   นักศึกษาต้องไม่สามารถดูตารางของกลุ่มอื่น งบประมาณ ผลการนิเทศ
    หรือผลประเมินของนักศึกษาคนอื่นได้
-   นักศึกษาเห็นเฉพาะนัดที่มีชื่อตนเองและไม่ใช่ฉบับร่าง
    เมื่อรายการเสร็จแล้วให้แสดงอาจารย์ที่เข้าร่วมจริงแทนรายชื่อที่วางแผนไว้

## 1.3.4 รอบสหกิจศึกษาและสถานะการปฏิบัติงาน

-   Prototype มีข้อมูลตัวอย่างรอบภาคเรียนที่ 2 ภาคฤดูร้อน และภาคเรียนที่ 1
    โดยไม่ได้กำหนดกฎชั้นปีที่ 4 หรือชั้นปีที่ 5 เป็น validation ใน UI
-   แต่ละรอบต้องกำหนดปีการศึกษา ภาคเรียน รุ่นนักศึกษา ช่วงเปิดยื่นสถานประกอบการ
    ช่วงฝึกงาน และสถานะของรอบ
-   สถานะของรอบประกอบด้วย ฉบับร่าง เปิดยื่นสถานประกอบการ ปิดรับคำร้อง
    กำลังฝึกงาน และปิดรอบ
-   รอบสถานะฉบับร่างใช้สำหรับเตรียมข้อมูลและเพิ่มนักศึกษาเข้ารอบ
-   นักศึกษาส่งคำร้องใหม่ได้เฉพาะเมื่อรอบอยู่ในสถานะเปิดยื่นสถานประกอบการ
-   เมื่อรอบปิดรับคำร้อง นักศึกษาไม่สามารถสร้างคำร้องใหม่
    แต่อาจารย์และนักศึกษายังดำเนินการกับคำร้องที่มีอยู่แล้วได้
-   รอบสถานะกำลังฝึกงานใช้สำหรับจัดตาราง บันทึกผลนิเทศ และประเมินผล
-   เมื่อปิดรอบ ข้อมูลในรอบเปลี่ยนเป็นข้อมูลประวัติและไม่สามารถสร้างรายการใหม่ได้
-   เจ้าหน้าที่และอาจารย์เลือกรอบบน Dashboard และหน้าที่มี cycle context ได้
    ส่วนนักศึกษาเห็นรอบปัจจุบันของตนเอง
-   Prototype แสดงข้อมูลและ timeline ของรอบแบบอ่านอย่างเดียว
    ยังไม่มีหน้าสร้าง แก้ไข ย้อนสถานะ หรือเพิ่มนักศึกษาเข้ารอบแบบกลุ่ม
-   นักศึกษาคนเดิมสามารถมีประวัติอยู่ได้หลายรอบในหลายปีการศึกษา
    แต่มีรอบที่กำลังดำเนินการได้เพียงหนึ่งรอบ
-   เจ้าหน้าที่แก้รอบของนักศึกษารายบุคคลจากหน้าข้อมูลนักศึกษาได้
    แต่ยังไม่มี flow ย้ายรอบพร้อมเหตุผลหรือประวัติการย้ายโดยเฉพาะ
-   คำร้อง ชุดหนังสือ ตารางนิเทศ ผลการนิเทศ และการประเมิน
    ต้องอ้างอิงรอบฝึกงานเดียวกันเพื่อไม่ให้ข้อมูลข้ามรอบ
-   สถานะการปฏิบัติงานของนักศึกษาในแต่ละรอบประกอบด้วย
    ยังไม่เริ่มปฏิบัติงาน กำลังปฏิบัติงาน ปฏิบัติงานเสร็จแล้ว และยุติการปฏิบัติงาน
-   เมื่ออาจารย์ยืนยันสถานประกอบการ สถานะการปฏิบัติงานเริ่มต้นเป็นยังไม่เริ่มปฏิบัติงาน
-   Prototype แสดงสถานะการปฏิบัติงาน แต่ยังไม่มี action เปลี่ยนสถานะ
    หรือบันทึกเหตุผลและประวัติการเปลี่ยนสถานะ
-   สถานะการปฏิบัติงานไม่เปลี่ยนอัตโนมัติตามวันที่ ตารางนิเทศ หรือผลประเมิน
-   ขอบเขตเริ่มต้นไม่รองรับกระบวนการเปลี่ยนสถานประกอบการระหว่างปฏิบัติงาน
    หากนักศึกษาหยุดฝึกหรือเกิดกรณีพิเศษ เจ้าหน้าที่บันทึกเป็นยุติการปฏิบัติงาน
    โดยเก็บสถานประกอบการ ตารางนิเทศ และข้อมูลที่เกิดขึ้นแล้วไว้เป็นประวัติ

## 1.3.5 ขั้นตอนการยื่นสถานประกอบการ

### 1. นักศึกษาส่งคำร้องรายบุคคล

-   นักศึกษาค้นหาและเลือกสถานประกอบการที่มีอยู่ในระบบ
-   หากไม่พบ นักศึกษาสามารถเพิ่มชื่อ ที่อยู่ และจังหวัดของสถานประกอบการใหม่ได้
-   จังหวัดเป็นข้อมูลบังคับ และระบบกำหนดภูมิภาคจากจังหวัด
    เพื่อใช้ค้นหา กรอง และวางแผนพื้นที่นิเทศ
-   สถานประกอบการที่เพิ่มใหม่ต้องมีสถานะรอเจ้าหน้าที่ตรวจสอบ
    แต่สามารถถูกเลือกใช้โดยนักศึกษาคนอื่นได้ เพื่อป้องกันการสร้างข้อมูลซ้ำ
-   นักศึกษาแต่ละคนกรอกตำแหน่งฝึกงาน รายละเอียดแบบไม่บังคับ ชื่อผู้รับหนังสือ
    ตำแหน่งหรือหน่วยงานของผู้รับ และที่อยู่สำหรับออกหนังสือของคำร้องตนเอง
-   ตามพฤติกรรมของ Prototype นักศึกษาแต่ละคนมีคำร้องที่กำลังดำเนินการได้
    ครั้งละหนึ่งรายการในระบบ หากถูกส่งกลับต้องแก้และส่งคำร้องเดิม
-   นักศึกษาไม่สามารถสร้างหรือแก้ไขคำร้องแทนนักศึกษาคนอื่นได้
-   นักศึกษาแก้ไขข้อมูลคำร้องของตนเองได้ตราบใดที่คำร้องยังไม่ถูกรวมในชุดหนังสือ
-   เมื่อคำร้องถูกรวมในชุดหนังสือแล้ว ข้อมูลคำร้องถูกล็อก
    และนักศึกษาต้องให้เจ้าหน้าที่ส่งกลับมาแก้ไข

### 2. เจ้าหน้าที่ตรวจคำร้องและจัดการเอกสารรายบุคคล

-   เมื่อนักศึกษายืนยันสถานประกอบการ ระบบสร้างคำร้องและแจ้งเจ้าหน้าที่ที่ใช้งานอยู่ทันที
-   เจ้าหน้าที่ตรวจข้อมูลคำร้อง แนบหนังสือขอความอนุเคราะห์ และตรวจหนังสือตอบรับรายคำร้อง
-   เจ้าหน้าที่ส่งกลับหนังสือตอบรับให้แก้ไข หรือยืนยันสถานประกอบการได้
-   อาจารย์ไม่มี route เมนู หรือ endpoint สำหรับดำเนินการใน flow นี้

### 3. เจ้าหน้าที่จัดทำหนังสือขอฝึกงาน

-   เจ้าหน้าที่แนบไฟล์ PDF หนังสือขอความอนุเคราะห์ให้คำร้องแต่ละรายการ
-   เอกสารเก็บประวัติรุ่น metadata ผู้ทำรายการ และตรวจสิทธิ์ก่อนดาวน์โหลด

### 4. การดำเนินการกับสถานประกอบการภายนอกระบบ

-   นักศึกษานำหนังสือไปส่งและประสานงานกับสถานประกอบการภายนอกระบบ
-   นักศึกษาแนบหนังสือตอบรับกลับเข้าคำร้องของตนเอง

### 5. เจ้าหน้าที่ตรวจสอบและยืนยันผลรายบุคคล

-   เจ้าหน้าที่ตรวจสอบ PDF ตอบกลับ ข้อมูลนักศึกษา และข้อมูลที่เกี่ยวข้อง
-   หากเอกสารไม่ถูกต้อง เจ้าหน้าที่ส่งกลับให้แก้ไขพร้อมระบุเหตุผลได้
-   นักศึกษาหนึ่งคนสามารถมีสถานประกอบการที่ได้รับการยืนยันแล้ว
    ได้เพียงหนึ่งแห่งต่อหนึ่งรอบฝึกงาน
-   คำร้องที่ยกเลิกหรือสิ้นสุดแล้วสามารถเก็บไว้เป็นประวัติได้
-   เมื่อเจ้าหน้าที่ยืนยันแล้ว กระบวนการยื่นสถานประกอบการของนักศึกษาคนนั้นถือว่าเสร็จสิ้น
    และข้อมูลพร้อมนำไปใช้ในการจัดสรรอาจารย์และวางแผนการนิเทศ

### 6. สถานะงานตรวจคำร้องรายบุคคล

-   รอตรวจคำร้อง
-   ส่งกลับแก้ไข
-   รอเอกสารตอบกลับ
-   รอตรวจผล
-   ยืนยันสถานประกอบการ
-   ไม่ได้รับการตอบรับ
-   ยกเลิก

สถานะคำร้องใช้ร่วมกันระหว่างหน้าของนักศึกษาและเจ้าหน้าที่ โดยอาจารย์ไม่เข้าถึง flow นี้

## 1.3.6 ขั้นตอนการจัดกลุ่ม ตาราง ผล และการประเมินการนิเทศ

### 1. เจ้าหน้าที่จัดกลุ่มนิเทศ

-   เจ้าหน้าที่เลือกบริบทเป็นรอบฝึกงานและครั้งที่นิเทศ 1 หรือ 2 ก่อนสร้างกลุ่ม
-   กลุ่มต้องมีชื่อและสถานประกอบการอย่างน้อย 1 แห่ง โดยเพิ่มอาจารย์ตอนตรวจกลุ่มเสนอหรือภายหลังได้
-   เลือกได้เฉพาะอาจารย์ที่ข้อมูลยังใช้งาน บัญชีไม่ถูกระงับหรือยุติ
    และยังไม่อยู่กลุ่มอื่นในรอบกับครั้งที่นิเทศเดียวกัน
-   สถานประกอบการหนึ่งแห่งอยู่ได้ไม่เกินหนึ่งกลุ่มในรอบกับครั้งที่นิเทศเดียวกัน
    ส่วนรอบหรือครั้งที่นิเทศอื่นจัดกลุ่มใหม่แยกจากกันได้
-   นักศึกษาไม่ถูกเลือกเป็นสมาชิกกลุ่มโดยตรง แต่ระบบอนุมานจากนักศึกษา
    ที่มีสถานที่ฝึกงานยืนยันแล้วในสถานประกอบการของกลุ่ม
-   Prototype รองรับการสร้างและดูรายละเอียดกลุ่ม แต่ยังไม่มีการแก้ไขหรือลบกลุ่ม

### 2. ขอบเขตตารางนิเทศของเจ้าหน้าที่

-   หน้าตารางนิเทศของเจ้าหน้าที่ใช้ติดตามรายการและประเมินสถานประกอบการหลังนิเทศเสร็จ
    เลือกดูตามรอบ ครั้งที่นิเทศ สถานะ กลุ่ม หรือสถานประกอบการได้
-   เจ้าหน้าที่ดูสถานประกอบการ นักศึกษา กลุ่ม อาจารย์ตามแผน
    อาจารย์ที่เข้าร่วมจริง และความคืบหน้าการประเมินของแต่ละรายการได้
-   Prototype ยังไม่มีหน้าสำหรับเจ้าหน้าที่สร้างรายการนัด เผยแพร่ เลื่อน ยกเลิก
    เปลี่ยนอาจารย์ในรายการ หรือบันทึกงบประมาณและค่าใช้จ่าย
-   รายการนัดที่เห็นในปัจจุบันเป็นข้อมูลตัวอย่างของ Prototype
    การนำไปทำ Backend ต้องกำหนดผู้สร้างและ transition ของสถานะเพิ่มเติม

### 3. การเข้าร่วมและการดำเนินการของอาจารย์

-   สถานะรายการนิเทศประกอบด้วย ฉบับร่าง (`draft`) รอการนิเทศ (`published`)
    เลื่อน (`postponed`) นิเทศเสร็จแล้ว (`completed`) และยกเลิก (`cancelled`)
-   อาจารย์ทุกคนเห็นรายการของทุกกลุ่มในรอบและครั้งที่นิเทศที่เลือก
    และเข้าร่วมหรือถอนตัวจากรายการที่ยังไม่เสร็จและไม่ถูกยกเลิกได้
-   การเข้าร่วมรายการของกลุ่มอื่นมีผลเฉพาะรายการนั้น
    ไม่เปลี่ยนกลุ่มรับผิดชอบหลักของอาจารย์
-   อาจารย์จัดการรายละเอียดรายการได้เมื่อเป็นสมาชิกกลุ่มรับผิดชอบ
    หรือเป็นผู้เข้าร่วมรายการนั้น
-   หน้ารายละเอียดเปิดให้แก้วันที่ ช่วงเช้าหรือบ่าย และรายชื่ออาจารย์ผู้เข้าร่วม
    แต่ Prototype ยังไม่มีปุ่มบันทึกตารางแยก ค่าจะถูกบันทึกเมื่อยืนยันนิเทศเสร็จแล้วเท่านั้น
-   ก่อนยืนยันนิเทศเสร็จแล้วต้องมีวันที่และอาจารย์อย่างน้อย 1 คน
    รายชื่อที่เลือก ณ ตอนยืนยันจะเป็นรายชื่อผู้เข้าร่วมจริง
-   เมื่อเสร็จแล้ว ระบบล็อกวันที่ ช่วงเวลา และผู้เข้าร่วมจริง
    แต่ข้อความผลการนิเทศยังแก้ไขได้ใน Prototype
-   รายการที่ยกเลิกดูได้อย่างเดียวและไม่สามารถประเมินผลได้
-   Prototype ยังไม่มี action ให้ผู้ใช้สร้าง เผยแพร่ เลื่อน หรือยกเลิกรายการนัด
    ไม่มีการตรวจเวลาชน และไม่มีประวัติการแก้ตาราง

### 4. การบันทึกผลการนิเทศ

-   ผลการนิเทศประกอบด้วยสรุปผล ปัญหาที่พบ ข้อเสนอแนะ
    และความต้องการของสถานประกอบการ โดยทุกช่องเป็นข้อความที่ไม่บังคับกรอก
-   ผลผูกกับรายการนัดหนึ่งรายการและใช้ร่วมกันระหว่างอาจารย์ผู้เข้าร่วม
-   การประเมินเปิดได้เมื่อรายการมีสถานะนิเทศเสร็จแล้วเท่านั้น
-   ความครบถ้วนของรายการคำนวณจากแบบประเมินนักศึกษาที่ต้องส่งทั้งหมด
    และแบบประเมินสถานประกอบการร่วมหนึ่งชุด แสดงเป็นยังไม่เริ่ม กำลังประเมิน หรือครบถ้วน

### 5. การประเมินนักศึกษารายบุคคล

-   อาจารย์ผู้เข้าร่วมนิเทศจริงทุกคนประเมินนักศึกษาแต่ละคนในรายการแยกจากกัน
-   แบบประเมินนักศึกษาของอาจารย์แต่ละคนแยกจากกัน และไม่ใช้แบบประเมินร่วมกัน
-   ใช้มาตราส่วน 5 ระดับ ได้แก่ 1 ต้องปรับปรุงอย่างมาก 2 ต้องปรับปรุง
    3 ผ่านตามเกณฑ์ 4 ดี และ 5 ดีมาก พร้อมตัวเลือกไม่สามารถประเมินได้
-   หน้ากรอกคะแนนนักศึกษาแสดงหัวข้อและระดับคะแนนในรูปแบบตาราง
    โดยเลือกได้หนึ่งค่าต่อหนึ่งหัวข้อ เพื่อให้ประเมินหลายหัวข้อต่อเนื่องได้สะดวก
-   หัวข้อประเมินนักศึกษาประกอบด้วย
    ความรับผิดชอบและตรงต่อเวลา วินัยและจรรยาบรรณในการทำงาน
    การสื่อสารและการทำงานร่วมกับผู้อื่น การประยุกต์ใช้ความรู้กับงาน
    คุณภาพและความก้าวหน้าของงาน การเรียนรู้และแก้ไขปัญหา
    และการปฏิบัติตามกฎหรือความปลอดภัยของสถานประกอบการ
-   อาจารย์สามารถบันทึกจุดเด่น ปัญหาที่พบ ข้อเสนอแนะ
    และเรื่องที่ต้องติดตามในการนิเทศครั้งถัดไปเป็นข้อความเพิ่มเติมได้
-   ระบบคำนวณคะแนนเฉลี่ยจากหัวข้อที่มีคะแนน โดยไม่นำหัวข้อที่เลือก
    ไม่สามารถประเมินได้มาคำนวณ
-   แบบประเมินมีสถานะฉบับร่างและส่งแบบประเมินแล้ว
    โดยจะส่งได้เมื่อทุกหัวข้อมีคะแนนหรือเลือกไม่สามารถประเมินได้ครบถ้วน
-   อาจารย์แก้ไขแบบประเมินฉบับร่างของตนเองได้
    แต่เมื่อยืนยันส่งแบบประเมินแล้วจะไม่สามารถแก้ไขหรือลบได้

### 6. การประเมินสถานประกอบการ

-   หนึ่งรายการนิเทศมีแบบประเมินสถานประกอบการร่วมหนึ่งชุด
    โดยอาจารย์คนแรกในรายชื่อผู้เข้าร่วมจริงเป็นผู้รับผิดชอบ
-   ใช้มาตราส่วนและวิธีคำนวณเดียวกับการประเมินนักศึกษา
-   หัวข้อประเมินสถานประกอบการประกอบด้วย
    ความเหมาะสมของงานกับสาขาวิชา ปริมาณและความท้าทายของงาน
    ความพร้อมของผู้ควบคุมงาน
    การดูแลและให้คำแนะนำนักศึกษา สภาพแวดล้อมและความปลอดภัย
    ความพร้อมของอุปกรณ์หรือทรัพยากร และการประสานงานกับมหาวิทยาลัย
-   ความเหมาะสมในการรับนักศึกษารุ่นถัดไปให้บันทึกเป็นผลสรุปแยกจากคะแนน ได้แก่
    แนะนำให้ส่งนักศึกษารุ่นถัดไป แนะนำแบบมีเงื่อนไข ต้องติดตามข้อมูลเพิ่มเติม
    ไม่แนะนำ หรือมีประเด็นเร่งด่วนด้านความปลอดภัย
-   อาจารย์สามารถบันทึกข้อสังเกต ความต้องการของสถานประกอบการ
    ปัญหาที่พบ และข้อเสนอแนะเพิ่มเติมได้
-   แบบประเมินมีสถานะฉบับร่างและส่งแบบประเมินแล้ว
    โดยจะส่งได้เมื่อทุกหัวข้อมีคะแนนหรือเลือกไม่สามารถประเมินได้ครบถ้วน
-   อาจารย์แก้ไขแบบประเมินฉบับร่างของตนเองได้
    แต่เมื่อยืนยันส่งแบบประเมินแล้วจะไม่สามารถแก้ไขหรือลบได้
-   ระบบคำนวณค่าเฉลี่ยของสถานประกอบการจากหัวข้อที่มีคะแนนในแบบประเมินร่วม
    โดยไม่นำหัวข้อที่เลือกไม่สามารถประเมินได้มาคำนวณ

### 7. การมองเห็นผลการนิเทศและการประเมิน

-   เจ้าหน้าที่ดูสถานะและจำนวนแบบประเมินที่ส่งแล้วเทียบกับจำนวนที่ต้องส่งได้
    แต่หน้าติดตามปัจจุบันยังไม่เปิดข้อความผลการนิเทศหรือคะแนนรายข้อ
-   อาจารย์ดูข้อมูลนักศึกษาและประวัติการสมัครได้ทุกคน
    แต่ดูข้อมูลการนิเทศและทำแบบประเมินได้เฉพาะรายการที่ตนเองรับผิดชอบหรือเข้าร่วมจริง
-   อาจารย์แก้ไขแบบประเมินได้เฉพาะฉบับร่างของตนเอง
    และดูแบบประเมินที่ตนเองส่งแล้วได้โดยไม่สามารถแก้ไข
-   นักศึกษาดูได้เฉพาะสถานะของรายการนิเทศตนเอง
    แต่ไม่สามารถดูงบประมาณ บันทึกภายใน คะแนน หรือผลประเมินได้
-   ผลประเมินของนักศึกษาแต่ละคนต้องไม่แสดงให้นักศึกษาคนอื่นหรือสถานประกอบการเห็น

## 1.3.7 การเข้าสู่ระบบและการจัดการบัญชีผู้ใช้

### 1. การสร้างบัญชี

-   ระบบมีบัญชีผู้ใช้ 3 บทบาท ได้แก่ เจ้าหน้าที่ อาจารย์ และนักศึกษา
-   ในขอบเขตเริ่มต้น บัญชีหนึ่งบัญชีมีได้หนึ่งบทบาท และชื่อผู้ใช้ต้องไม่ซ้ำกันทั้งระบบ
-   นักศึกษาและอาจารย์ไม่สามารถสมัครบัญชีด้วยตนเองได้
-   เมื่อเจ้าหน้าที่เพิ่มหรือนำเข้าข้อมูลนักศึกษา ระบบสร้างบัญชีนักศึกษาจากรหัสนักศึกษา
-   เมื่อเจ้าหน้าที่เพิ่มหรือนำเข้าข้อมูลอาจารย์ ระบบสร้างบัญชีอาจารย์จากรหัสอาจารย์
-   หากรหัสนักศึกษาหรือรหัสอาจารย์มีบัญชีอยู่แล้ว ระบบต้องเชื่อมกับบัญชีเดิม
    เมื่อบัญชีนั้นมีบทบาทตรงกัน และรายงานรายการซ้ำให้เจ้าหน้าที่ทราบโดยไม่สร้างบัญชีซ้ำ
-   หากชื่อผู้ใช้เดียวกันมีอยู่ในบทบาทอื่น ระบบต้องหยุดรายการดังกล่าว
    และแจ้งให้ผู้ดูแลระบบตรวจสอบ โดยไม่เชื่อมข้อมูลข้ามบทบาท
-   บัญชีเจ้าหน้าที่จัดเตรียมโดยผู้ดูแลระบบภายนอกขั้นตอนการใช้งานปกติ
    โดยใช้รหัสบุคลากรหรือชื่อผู้ใช้ที่มหาวิทยาลัยกำหนด

### 2. การเข้าสู่ระบบครั้งแรก

-   นักศึกษาใช้รหัสนักศึกษาเป็นทั้งชื่อผู้ใช้และรหัสผ่านเริ่มต้น
-   อาจารย์ใช้รหัสอาจารย์เป็นทั้งชื่อผู้ใช้และรหัสผ่านเริ่มต้น
-   รหัสผ่านเริ่มต้นใช้ได้เฉพาะการเข้าสู่ระบบครั้งแรกเท่านั้น
-   หลังตรวจสอบชื่อผู้ใช้และรหัสผ่านเริ่มต้นสำเร็จ
    ระบบต้องนำผู้ใช้ไปตั้งรหัสผ่านใหม่ก่อนเข้าถึงส่วนอื่นของระบบ
-   ผู้ใช้ไม่สามารถข้ามขั้นตอนตั้งรหัสผ่านใหม่ได้
    และรหัสผ่านใหม่ต้องไม่ตรงกับชื่อผู้ใช้หรือรหัสผ่านเริ่มต้น
-   รหัสผ่านใหม่ต้องมีความยาวอย่างน้อย 8 ตัวอักษร
    และประกอบด้วยตัวอักษรกับตัวเลขอย่างน้อยอย่างละหนึ่งตัว

### 3. การเข้าสู่ระบบตามปกติและ Session

-   ผู้ใช้กรอกชื่อผู้ใช้และรหัสผ่านเพื่อเข้าสู่ระบบ
-   ระบบตรวจสอบข้อมูลบัญชี รหัสผ่าน สถานะบัญชี และบทบาทก่อนสร้าง Session
-   เมื่อเข้าสู่ระบบสำเร็จ ระบบนำผู้ใช้ไปยังหน้าหลักตามบทบาท
-   Prototype จำลอง Session ในฝั่ง client และยังไม่ได้บังคับอายุ Session 8 ชั่วโมง
    อายุ Session จริงต้องกำหนดเมื่อพัฒนา Backend
-   เมื่อผู้ใช้กดออกจากระบบ ระบบต้องยกเลิก Session ปัจจุบันทันที
-   ข้อความเมื่อเข้าสู่ระบบไม่สำเร็จต้องไม่ระบุว่าชื่อผู้ใช้หรือรหัสผ่านส่วนใดผิด
    เพื่อไม่เปิดเผยว่าบัญชีใดมีอยู่ในระบบ
-   Prototype ล็อกการลองเข้าสู่ระบบชั่วคราว 1 นาทีเมื่อกรอกผิดครบ 3 ครั้ง
    เพื่อสาธิต interaction เท่านั้น ค่า production และการเก็บตัวนับฝั่ง server ต้องยืนยันอีกครั้ง

### 4. สถานะบัญชี

-   สถานะบัญชีประกอบด้วย รอเข้าสู่ระบบครั้งแรก ใช้งาน ระงับชั่วคราว
    และยุติการใช้งาน
-   บัญชีที่รอเข้าสู่ระบบครั้งแรกสามารถใช้ได้เฉพาะรหัสผ่านเริ่มต้น
    และเปลี่ยนเป็นสถานะใช้งานเมื่อตั้งรหัสผ่านใหม่สำเร็จ
-   บัญชีที่ถูกระงับชั่วคราวหรือยุติการใช้งานไม่สามารถสร้าง Session ใหม่ได้
-   การระงับหรือยุติการใช้งานบัญชีต้องยกเลิก Session ที่ยังใช้งานอยู่ทั้งหมด
-   การย้ายรอบฝึกงานไม่ทำให้บัญชีนักศึกษาถูกยกเลิกหรือสร้างบัญชีใหม่
-   เจ้าหน้าที่สามารถยุติการใช้งานบัญชีเมื่อนักศึกษาพ้นสภาพ
    หรือเมื่ออาจารย์สิ้นสุดการปฏิบัติงาน
-   การระงับหรือยุติการใช้งานบัญชีเจ้าหน้าที่ดำเนินการโดยผู้ดูแลระบบ
    ภายนอกขั้นตอนการใช้งานปกติ

### 5. การเปลี่ยนและรีเซ็ตรหัสผ่าน

-   ผู้ใช้ที่เข้าสู่ระบบแล้วสามารถเปลี่ยนรหัสผ่านของตนเองได้
    โดยต้องกรอกรหัสผ่านปัจจุบัน รหัสผ่านใหม่ และยืนยันรหัสผ่านใหม่
-   หากผู้ใช้ลืมรหัสผ่าน ให้ติดต่อเจ้าหน้าที่เพื่อรีเซ็ตรหัสผ่าน
    โดยขอบเขตเริ่มต้นยังไม่รวมการรีเซ็ตผ่านอีเมล SMS หรือ OTP
-   เจ้าหน้าที่กำหนดรหัสผ่านชั่วคราวใหม่ให้ผู้ใช้และส่งมอบรหัสผ่านภายนอกระบบ
-   รหัสผ่านชั่วคราวต้องยาวอย่างน้อย 8 ตัว มีตัวอักษรและตัวเลข
    และต้องไม่ตรงกับรหัสนักศึกษาหรือรหัสอาจารย์
-   หลังรีเซ็ตรหัสผ่าน ระบบยกเลิก Session เดิมทั้งหมด
    และบังคับให้ผู้ใช้เปลี่ยนรหัสผ่านชั่วคราวเมื่อเข้าสู่ระบบครั้งถัดไป
-   รหัสผ่านชั่วคราวจากการรีเซ็ตต้องไม่กำหนดเป็นรหัสนักศึกษาหรือรหัสอาจารย์ซ้ำ

### 6. การควบคุมสิทธิ์และประวัติการใช้งาน

-   ทุกหน้าจอที่ต้องยืนยันตัวตนและทุกการดำเนินการภายในระบบ
    ต้องตรวจสอบ Session และบทบาทของผู้ใช้
-   เมนู route และ endpoint ตรวจคำร้องกับเอกสารอนุญาตเฉพาะเจ้าหน้าที่
    อาจารย์ไม่มีสิทธิ์เข้าถึง flow นี้
-   การตรวจสอบสิทธิ์ฝั่ง Backend ต้องตรวจทั้งบทบาทและขอบเขตข้อมูล
    เช่น นักศึกษาเข้าถึงได้เฉพาะข้อมูลของตนเอง
    ส่วนอาจารย์ค้นหา ดูประวัติ และแก้ไขชื่อกับนามสกุลของนักศึกษาได้ทุกคน
    แต่เข้าถึงข้อมูลการนิเทศและการประเมินได้เฉพาะรายการที่ตนเองรับผิดชอบหรือเข้าร่วม
-   หน้ารายละเอียดบุคคลแสดงประวัติกิจกรรมบัญชีจากข้อมูลตัวอย่าง
    ส่วนการบันทึก audit log จริงของการเข้าสู่ระบบ การออกจากระบบ เปลี่ยนหรือรีเซ็ตรหัสผ่าน
    ระงับ และยุติบัญชี ยังต้องพัฒนาใน Backend พร้อมวันเวลาและผู้ดำเนินการ
-   ระบบต้องเก็บรหัสผ่านในรูปแบบที่ไม่สามารถอ่านกลับเป็นข้อความเดิมได้
    และต้องไม่แสดงรหัสผ่านปัจจุบันหรือรหัสผ่านเดิมแก่เจ้าหน้าที่

## 1.3.8 การนำเข้า ส่งออก และยุติการใช้งานข้อมูลหลัก

### 1. ข้อมูลขั้นต่ำ

-   ข้อมูลขั้นต่ำของนักศึกษาประกอบด้วยรหัสนักศึกษา คำนำหน้าชื่อ ชื่อ และนามสกุล
-   ข้อมูลขั้นต่ำของอาจารย์ประกอบด้วยรหัสอาจารย์ คำนำหน้าชื่อ ชื่อ และนามสกุล
-   รหัสนักศึกษาและรหัสอาจารย์ต้องไม่ว่างและต้องไม่ซ้ำกันภายในประเภทข้อมูลเดียวกัน
-   รหัสนักศึกษาและรหัสอาจารย์ที่ถูกใช้สร้างบัญชีแล้ว
    เปลี่ยนได้โดยเจ้าหน้าที่เท่านั้น และต้องปรับชื่อผู้ใช้ของบัญชีที่เชื่อมกันในรายการเดียวกัน
-   ทุกการแก้ไขรหัส ชื่อ นามสกุล และสถานะการใช้งาน
    ต้องเก็บผู้แก้ไข วันเวลา ค่าเดิม และค่าใหม่ไว้ในประวัติ

### 2. การนำเข้าข้อมูล

-   เจ้าหน้าที่สามารถนำเข้าข้อมูลนักศึกษาและอาจารย์ด้วยไฟล์ CSV หรือ Excel (.xlsx)
-   ไฟล์ต้องเป็น CSV หรือ Excel (.xlsx) ขนาดไม่เกิน 5 MB
-   ระบบมีไฟล์ตัวอย่างที่ระบุคอลัมน์รหัส คำนำหน้าชื่อ ชื่อ และนามสกุลให้ดาวน์โหลด
-   ก่อนยืนยันนำเข้า ระบบตรวจสอบไฟล์และแสดงจำนวนรายการที่ถูกต้อง รายการที่ซ้ำ
    และรายการที่ไม่ถูกต้อง พร้อมเหตุผลของแต่ละรายการ
-   รหัสที่ซ้ำกันมากกว่าหนึ่งแถวภายในไฟล์เดียวกันถือเป็นรายการไม่ถูกต้อง
-   รายการใหม่ที่ถูกต้องสร้างข้อมูลหลักและบัญชีที่รอเข้าสู่ระบบครั้งแรก
-   หากพบรหัสเดิมในประเภทข้อมูลเดียวกัน ระบบใช้คำนำหน้าชื่อ ชื่อ และนามสกุลจากไฟล์
    เพื่ออัปเดตข้อมูลเดิม โดยไม่สร้างบัญชีใหม่ ไม่เปลี่ยนรหัสผ่านปัจจุบัน
    และสำหรับนักศึกษาไม่เปลี่ยนรอบฝึกงานเดิม
-   รายการที่ไม่ถูกต้องไม่ถูกนำเข้า ส่วนรายการอื่นที่ถูกต้องสามารถนำเข้าได้เมื่อเจ้าหน้าที่ยืนยัน
-   หลังนำเข้า ระบบแสดงผลสรุปและเปิดให้ดาวน์โหลดรายการที่ไม่สำเร็จพร้อมเหตุผลได้

### 3. การส่งออกข้อมูล

-   เจ้าหน้าที่สามารถส่งออกข้อมูลนักศึกษาและอาจารย์เป็นไฟล์ CSV หรือ Excel (.xlsx)
-   ไฟล์นักศึกษาประกอบด้วยรหัส คำนำหน้าชื่อ ชื่อ นามสกุล รุ่น หมู่เรียน
    สถานประกอบการ และตำแหน่งที่ฝึก
-   ไฟล์อาจารย์ประกอบด้วยรหัส คำนำหน้าชื่อ ชื่อ และนามสกุล
-   การส่งออกข้อมูลไม่รวมรหัสผ่านหรือข้อมูลสำหรับยืนยันตัวตน
-   Prototype ส่งออกข้อมูลทั้งหมดของประเภทที่เลือก ไม่จำกัดตามคำค้นหาหรือตัวกรองในตาราง

### 4. การยุติการใช้งาน

-   ข้อมูลนักศึกษา อาจารย์ และสถานประกอบการที่เคยถูกใช้อ้างอิง
    ต้องไม่ถูกลบออกจากระบบ
-   เจ้าหน้าที่สามารถเปลี่ยนสถานะข้อมูลเป็นใช้งานหรือยุติการใช้งานได้
-   ข้อมูลที่ยุติการใช้งานไม่ปรากฏเป็นตัวเลือกสำหรับรายการใหม่
    แต่ยังค้นหาและแสดงในประวัติเดิมได้
-   การยุติการใช้งานนักศึกษาหรืออาจารย์ต้องยุติการใช้งานบัญชีที่เชื่อมกัน
-   การยุติการใช้งานสถานประกอบการไม่ยกเลิกคำร้อง ชุดหนังสือ
    หรือตารางนิเทศที่เกิดขึ้นก่อนหน้า

## 1.3.9 การแจ้งเตือนภายในระบบ

-   ระบบแจ้งเตือนเฉพาะภายในระบบ และไม่ส่งอีเมล SMS
    หรือข้อความผ่านบริการภายนอก
-   แต่ละบทบาทเห็นเฉพาะรายการตัวอย่างที่กำหนดให้บทบาทนั้น
    โดยแสดงหัวข้อ รายละเอียด วันเวลา สถานะอ่านแล้วหรือยังไม่อ่าน และประเภทเหตุการณ์
-   ผู้ใช้เปิดรายการเพื่อไปยังหน้าที่เกี่ยวข้อง ทำเครื่องหมายอ่านทีละรายการ
    หรือทำเครื่องหมายอ่านทั้งหมดได้
-   การแจ้งเตือนเป็นข้อมูลประกอบการติดตามเท่านั้น
    สถานะจริงของกระบวนการต้องอ่านจากคำร้อง ชุดหนังสือ หรือรายการนัดที่เกี่ยวข้อง
-   การกระทำในหน้าคำร้อง หนังสือ ตาราง และการประเมินของ Prototype
    ยังไม่สร้างการแจ้งเตือนใหม่โดยอัตโนมัติ รายการปัจจุบันเป็น seed data
    ดังนั้น event trigger และผู้รับจริงเป็นงาน Backend ที่ยังไม่ยืนยันจาก UI

## 1.3.10 ปฏิทินงานตามบทบาท

-   เจ้าหน้าที่ อาจารย์ และนักศึกษาสามารถเปิดปฏิทินงานของตนเองได้
-   ปฏิทินเป็นมุมมองรายเดือน แสดงเฉพาะกิจกรรมที่สัมพันธ์กับบทบาท
    เลือกเดือน วัน และกรองประเภทกิจกรรมได้
-   ประเภทกิจกรรมประกอบด้วยนิเทศ เอกสาร กำหนดส่ง ประเมิน และทั่วไป
-   ระบบแสดงกิจกรรมตัวอย่างของระบบ รายการนัดนิเทศที่เกี่ยวข้อง
    และกิจกรรมที่ผู้ใช้เพิ่มเองในปฏิทินเดียวกัน
-   ผู้ใช้เพิ่มกิจกรรมได้โดยต้องระบุชื่อ วันที่ และประเภท
    ส่วนรายละเอียดเป็นข้อมูลไม่บังคับ
-   กิจกรรมที่เชื่อมกับงานในระบบต้องเปิดไปยังหน้ารายละเอียดหรือหน้าดำเนินการที่เกี่ยวข้องได้
-   Prototype ยังไม่มีการแก้ไขหรือลบกิจกรรม และข้อมูลที่เพิ่มไม่คงอยู่เมื่อโหลดใหม่
    รวมถึงยังไม่ผูก business action ทุกหน้ามาสร้างหรืออัปเดตกิจกรรมอัตโนมัติ

## 1.3.11 การจัดการสถานประกอบการและไฟล์เอกสาร

### 1. ข้อมูลพื้นที่และสถานะสถานประกอบการ

-   เจ้าหน้าที่และอาจารย์ใช้ทะเบียนสถานประกอบการร่วมกัน
    และสามารถค้นหา ดู เพิ่ม แก้ไข ยุติการใช้งาน กู้คืน และลบได้ตามเงื่อนไข
-   ข้อมูลบังคับประกอบด้วยชื่อ สาขา จังหวัด ภูมิภาค ที่อยู่
    ชื่อผู้ติดต่อ และเบอร์โทรศัพท์ผู้ติดต่อ
-   ในแบบฟอร์มของเจ้าหน้าที่และอาจารย์ ผู้ใช้เลือกจังหวัดและภูมิภาคแยกกัน
    Prototype ยังไม่คำนวณภูมิภาคจากจังหวัดอัตโนมัติใน flow นี้
-   ทะเบียนหลักมีสถานะใช้งานและยุติการใช้งาน
    รายการที่ยุติแล้วไม่เป็นตัวเลือกสำหรับงานใหม่ แต่ยังดูและกู้คืนได้
-   ลบถาวรได้เฉพาะสถานประกอบการที่ยังไม่ถูกอ้างอิงจากนักศึกษาหรือคำร้อง
-   นักศึกษาสามารถเพิ่มสถานประกอบการแบบย่อจากหน้าสร้างคำร้อง
    โดยกรอกชื่อ ที่อยู่ และจังหวัด ระบบกำหนดภูมิภาคและสถานะรอตรวจสอบให้
-   รายการที่นักศึกษาเพิ่มอยู่ใน mock store แยกจากทะเบียนหลักของเจ้าหน้าที่และอาจารย์
    Prototype ยังไม่มีหน้าตรวจสอบ อนุมัติ แก้ไข หรือรวมรายการซ้ำ
    จึงยังไม่มี workflow ที่ทำให้สถานะรอตรวจสอบเปลี่ยนเป็นใช้งาน

### 2. ข้อกำหนดไฟล์ PDF

-   หน้าเอกสารของเจ้าหน้าที่รับหนังสือขอฝึกงานนามสกุล `.pdf` ขนาดไม่เกิน 10 MB
-   การตรวจใน Prototype ใช้ชื่อไฟล์กับขนาดเท่านั้น ยังไม่ตรวจ MIME type
    หรือลายเซ็นเนื้อหา PDF และไม่ได้เก็บ binary จริง
-   เอกสารและประวัติฉบับที่แสดงอยู่เป็น metadata จาก seed data
    การดาวน์โหลดเรียก endpoint ที่สร้าง mock PDF ตามชื่อไฟล์
-   หนังสือตอบกลับมีให้ทดสอบเฉพาะชุดหนังสือตัวอย่างที่กำหนดไว้
    Prototype ไม่มีหน้าสำหรับนักศึกษาอัปโหลด ดาวน์โหลด หรือจัดการฉบับเอกสาร
-   เจ้าหน้าที่เป็นผู้ตรวจเอกสาร ส่งกลับให้แก้ไขพร้อมเหตุผล หรือยืนยันผลรายนักศึกษา
-   การจัดเก็บไฟล์จริง การตรวจ PDF จากเนื้อหา การควบคุมสิทธิ์ดาวน์โหลด
    versioning และผู้ทำรายการต้องพัฒนาใน Backend/File Storage

### 3. ขอบเขตรายงาน

-   ขอบเขตเริ่มต้นไม่มีระบบสร้างหรือส่งออกรายงานสถานประกอบการ
    ตารางนิเทศ ผลประเมิน หรืองบประมาณ
-   การส่งออกจำกัดเฉพาะข้อมูลนักศึกษาและอาจารย์ตามที่กำหนด
    ในหัวข้อการนำเข้าและส่งออกข้อมูลหลัก

## 1.3.12 รายการสมัครสถานประกอบการส่วนตัวของนักศึกษา

### 1. วัตถุประสงค์และขอบเขตข้อมูล

-   รายการสมัครเป็นเครื่องมือให้นักศึกษาติดตามการสมัครงานหรือฝึกงานหลายแห่งด้วยตนเอง
    และไม่ใช่คำร้องขอออกหนังสืออย่างเป็นทางการในหัวข้อ 1.3.5
-   นักศึกษาหนึ่งคนมีรายการสมัครได้หลายสถานประกอบการพร้อมกัน
    เพิ่ม แก้ไข เปลี่ยนสถานะ และลบรายการของตนเองได้
-   ข้อมูลรายการประกอบด้วยสถานประกอบการ ตำแหน่ง จังหวัด วันที่สมัคร
    สถานะ และหมายเหตุสำหรับติดตาม
-   การแก้สถานะในรายการสมัครไม่สร้างหรือแก้คำร้องขอออกหนังสือ
    ไม่ยืนยันสถานที่ฝึกงาน และไม่เปลี่ยนสถานะการปฏิบัติงานอัตโนมัติ

### 2. สถานะและการแสดงผล

-   สถานะประกอบด้วยส่งใบสมัครแล้ว รอการตอบกลับ ได้รับการตอบกลับ
    รอสัมภาษณ์ ตอบรับ และไม่ผ่าน
-   หน้าของนักศึกษาแสดงสรุปจำนวนตามสถานะ ค้นหา กรอง เรียงลำดับ
    แบ่งหน้า และสลับระหว่างตาราง desktop กับ card บน mobile
-   เจ้าหน้าที่และอาจารย์มีหน้าภาพรวมแบบอ่านอย่างเดียว
    เลือกบริบทตามรุ่น หมู่เรียน และภาคเรียน ค้นหานักศึกษา
    กรองสถานะหรือจังหวัด และเปิดดูรายการทุกแห่งของนักศึกษาแต่ละคนได้
-   รายการสมัครใน Prototype เป็น mock data แยกจากข้อมูลคำร้องและสถานที่ฝึกงาน
    Backend ต้องคงขอบเขต ownership ของนักศึกษาและความเป็นอิสระของสอง flow นี้

## 1.3.13 Dashboard การค้นหา และพฤติกรรม UI ร่วม

### 1. Dashboard ตามบทบาท

-   หลังเข้าสู่ระบบ ผู้ใช้ถูกนำไป Dashboard ตามบทบาท
-   Dashboard เจ้าหน้าที่และอาจารย์เลือกดูรอบฝึกงานที่มีใน Prototype ได้
    ส่วน Dashboard นักศึกษาใช้รอบที่ผูกกับนักศึกษาปัจจุบัน
-   การ์ดสรุป รายการล่าสุด และทางลัดต้องแสดงเฉพาะข้อมูลและ action ที่บทบาทมีสิทธิ์
-   ตัวเลขและรายการใน Dashboard ปัจจุบันคำนวณจาก seed/mock store
    และอาจไม่เปลี่ยนตาม action ของทุกหน้าหาก store เหล่านั้นยังแยกจากกัน

### 2. ตารางและรายการข้อมูล

-   หน้ารายการใช้รูปแบบจาก `/dev/ui` เป็นมาตรฐาน ได้แก่หัวข้อกับ primary action
    ช่องค้นหา ตัวกรองด้านขวา ปุ่มล้างตัวกรองแบบ icon-only และ active-filter chips
-   ตาราง desktop รองรับหัวข้อเรียงลำดับ row action และ footer แบ่งหน้า
    ส่วนหน้าจอเล็กแสดงข้อมูลสำคัญในรูปแบบ card พร้อม action ที่เทียบเท่ากัน
-   หน้าที่โหลดข้อมูลต้องมีสถานะ loading, empty, error พร้อม retry และ data state
    โดย loading ใช้ skeleton ที่สอดคล้องกับ layout จริง
-   การค้นหาและตัวกรองทำงานกับข้อมูล mock ในหน่วยความจำ
    และต้องออกแบบ API ให้รองรับเงื่อนไขเดียวกันเมื่อเชื่อม Backend

### 3. Form และ feedback

-   ช่องบังคับแสดง validation ใกล้ช่องที่ผิด และปุ่ม submit ต้องป้องกันการกดซ้ำ
-   การลบหรือยุติการใช้งานใช้ dialog ยืนยันจาก component ของระบบ
    ไม่ใช้ browser `alert()` หรือ `confirm()`
-   การดำเนินการสำเร็จหรือผิดพลาดแสดง feedback ผ่าน toast หรือ inline state
-   Prototype บาง flow เก็บ state เฉพาะระหว่างใช้งานหน้าเว็บ
    การ refresh อาจคืนค่า seed data จึงไม่ถือว่าเป็นหลักฐานเรื่อง persistence

## 1.3.14 Route และหน้าจอที่เป็นหลักฐานของ Prototype

Route ต่อไปนี้คือหน้าจอที่มีอยู่จริง ณ วันที่ปรับเอกสาร
ใช้เป็น traceability ระหว่าง requirement กับ UI แต่ไม่รวม `/dev/ui` ซึ่งเป็นหน้ามาตรฐานภายในสำหรับนักพัฒนา

### 1. หน้าร่วมทุกบทบาท

| Route | หน้าที่ |
|---|---|
| `/login` | เข้าสู่ระบบและแสดงสถานะบัญชี |
| `/first-login` | บังคับตั้งรหัสผ่านในการเข้าสู่ระบบครั้งแรก |
| `/account/password` | เปลี่ยนรหัสผ่านของผู้ใช้ปัจจุบัน |
| `/` | Dashboard ตามบทบาท |
| `/calendar` | ปฏิทินงานและเพิ่มกิจกรรม |
| `/notifications` | รายการแจ้งเตือน อ่านทีละรายการหรืออ่านทั้งหมด |
| `/forbidden` | แจ้งว่าไม่มีสิทธิ์เข้าถึง route |

## 1.3.15 ขอบเขตที่ UI Prototype ยังไม่รองรับ

-   ยังไม่มี Backend จริง ฐานข้อมูล Prisma/MySQL authentication และ RBAC ฝั่ง server
    การเก็บไฟล์จริง หรือ persistence ของ business data
-   ยังไม่มีหน้าจัดการรอบฝึกงาน เช่นสร้าง แก้ไข เปิดรับ ปิดรับ เริ่มฝึก หรือปิดรอบ
-   ยังไม่มี workflow เจ้าหน้าที่สร้าง เผยแพร่ เลื่อน ยกเลิกตารางนิเทศ
    ตรวจตารางชน หรือบันทึกประวัติการเปลี่ยนแปลง
-   ยังไม่มีระบบงบประมาณ ค่าเดินทาง ค่าเบี้ยเลี้ยง ค่าที่พัก การเบิกจ่าย
    การแนบใบเสร็จ หรือการอนุมัติค่าใช้จ่าย
-   ยังไม่มีหน้าตรวจสอบหรือรวมสถานประกอบการที่นักศึกษาเพิ่ม
    และ mock store ของรายการดังกล่าวยังไม่เชื่อมทะเบียนหลัก
-   ยังไม่มีการอัปโหลดหนังสือตอบกลับโดยนักศึกษา การเก็บเอกสารจริง
    และการสร้าง PDF หนังสือจากข้อมูลในระบบ
-   มี automatic notification ถึงเจ้าหน้าที่เมื่อนักศึกษายืนยันสถานประกอบการ
    ส่วน event synchronization ระหว่างปฏิทิน ตารางนิเทศ และ Dashboard ยังต้องพัฒนาต่อ
-   ยังไม่มีรายงานหรือการส่งออกข้อมูลคำร้อง สถานประกอบการ ตารางนิเทศ
    ผลการนิเทศ และงบประมาณ โดยผลประเมินรองรับ CSV/XLSX ใน Prototype แล้ว
-   ยังไม่มีการเปลี่ยนสถานะการปฏิบัติงานของนักศึกษาใน UI
    และไม่มี logic เปลี่ยนสถานะอัตโนมัติตามวันที่หรือผลนิเทศ
