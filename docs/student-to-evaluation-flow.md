# Student-to-evaluation flow

เอกสารนี้อธิบาย flow ที่อ่านได้จาก implementation ปัจจุบัน ตั้งแต่นักศึกษาส่งเรื่องเลือกสถานประกอบการจนถึงอาจารย์ส่งผลประเมิน โดยใช้คำว่า **คำร้อง** หมายถึง `PlacementRequest` และแยกจาก **รายการสมัคร** (`StudentApplication`) ให้ชัดเจน

## ภาพรวม

```text
นักศึกษาสมัครบริษัท
  → บริษัทตอบรับ
  → นักศึกษายืนยันเลือกบริษัทและส่งคำร้อง
  → เจ้าหน้าที่ออกหนังสือ → นักศึกษาส่งหนังสือตอบรับ
  → เจ้าหน้าที่ยืนยันสถานที่ฝึกงาน
  → เจ้าหน้าที่จัดกลุ่ม/ตารางนิเทศและเผยแพร่
  → นิเทศเสร็จ → อาจารย์ประเมินนักศึกษาและสถานประกอบการ
```

ทุกขั้นที่เขียนว่า “ยืนยัน” เป็นคนละความหมาย: นักศึกษายืนยันเลือกบริษัท, เจ้าหน้าที่ยืนยันเอกสารตอบรับ, และอาจารย์ยืนยันผลการนิเทศ

## 1. นักศึกษาส่งรายการสมัคร

1. นักศึกษาที่มี session และ active enrollment สร้างรายการที่ `/student/applications` ผ่าน `POST /api/student/applications`.
2. ข้อมูลที่ต้องส่งผ่าน Zod schema ได้แก่ บริษัท, ตำแหน่ง, ที่อยู่บริษัท, ผู้รับหนังสือ, ที่อยู่สำหรับออกหนังสือ, จังหวัด และพิกัดละติจูด/ลองจิจูด (ต้องมีครบคู่หรือเว้นทั้งคู่).
3. ระบบบันทึก `StudentApplication` เป็น `SUBMITTED` ผูกกับ enrollment ของนักศึกษาในรอบสหกิจที่ active.
4. ระหว่างมีรายการที่ยังไม่ถูกบริษัทปฏิเสธ ระบบกันไม่ให้นักศึกษาสร้างรายการใหม่ใน enrollment เดียวกันด้วย uniqueness/`activeSlotKey`.

สถานะรายการสมัครเดินได้โดยสรุป: `submitted` → `waiting-response` / `responded` / `waiting-interview` → `accepted` หรือ `rejected`.

## 2. ยืนยันเลือกบริษัทและสร้างคำร้อง

1. เมื่อบริษัทตอบรับแล้ว สถานะรายการสมัครต้องเป็น `accepted`.
2. นักศึกษาเท่านั้นจึงเปลี่ยนเป็น `completed` ได้ โดย `PATCH /api/student/applications/:id`.
3. การเปลี่ยนครั้งนี้ทำใน transaction เดียว: ล็อกรายการสมัคร, สร้าง `PlacementRequest` สถานะ `SUBMITTED`, บันทึกประวัติสถานะ และส่ง notification ให้เจ้าหน้าที่ active ทุกคน.
4. คำร้อง snapshot ข้อมูลบริษัท/ตำแหน่ง/ผู้รับหนังสือ/ที่อยู่และพิกัดจากรายการสมัคร ณ เวลายืนยัน เพื่อใช้ทำหนังสือในภายหลัง.

ผลลัพธ์คือรายการสมัครที่เลือกแล้วแก้ไขหรือเลือกซ้ำไม่ได้ และคำร้องจะปรากฏที่ `/staff/requests`.

## 3. ออกหนังสือและรับหนังสือตอบรับ

| ผู้ดำเนินการ | การกระทำ | สถานะคำร้องหลังทำ |
| --- | --- | --- |
| เจ้าหน้าที่ | อัปโหลด PDF หนังสือขอความอนุเคราะห์ (`outgoing`) | `WAITING_RESPONSE` |
| นักศึกษา | ดาวน์โหลดเอกสาร ส่งให้สถานประกอบการ และอัปโหลด PDF หนังสือตอบรับ (`company-response`) | `WAITING_REVIEW` |
| เจ้าหน้าที่ | ตรวจและยืนยันเอกสาร | `CONFIRMED` |
| เจ้าหน้าที่ | ส่งเอกสารกลับพร้อมเหตุผล | `RETURNED` |

- ไฟล์ส่งผ่าน `POST /api/placement-requests/:id/documents`; server จำกัด role, ประเภทเอกสาร และสถานะที่ทำได้
- ทุกการอัปโหลดสร้าง version ใหม่ของเอกสาร และ version ที่ active เดิมจะถูก supersede
- เมื่อยืนยันคำร้อง ระบบสร้าง/ผูก `CompanySite` หากยังไม่มี, ตั้งข้อมูลการยืนยัน และแจ้งนักศึกษา
- `RETURNED` ทำให้นักศึกษาส่งเอกสารตอบรับฉบับแก้ไขได้อีกครั้ง; การยืนยันต้องมีเอกสารตอบรับที่ active

## 4. จัดแผนนิเทศ

หลังคำร้องเป็น `CONFIRMED` เท่านั้นจึงเป็นข้อมูลที่ใช้วางแผนนิเทศได้

1. เจ้าหน้าที่เลือกบริษัทที่ยืนยันแล้วในรอบสหกิจและครั้งที่นิเทศ เพื่อสร้าง `SupervisionGroup` ที่ `/staff/supervision/groups`.
2. เจ้าหน้าที่กำหนดอาจารย์ประจำกลุ่ม หรือใช้ผลช่วยจัดกลุ่มตามข้อมูลพื้นที่; server ป้องกันบริษัทถูกอยู่ซ้ำในกลุ่ม/รอบเดียวกัน.
3. เจ้าหน้าที่สร้าง `SupervisionAppointment` ระบุ กลุ่ม บริษัท นักศึกษา วันที่ ช่วงเวลา และอาจารย์. หากเลือก publish ระบบตั้งสถานะ `PUBLISHED` และแจ้งทั้งนักศึกษาและอาจารย์.
4. ตารางที่เผยแพร่แสดงแก่ผู้เกี่ยวข้องที่ `/student/supervision` และ `/lecturer/supervision`.

## 5. บันทึกผลนิเทศและปลดล็อกการประเมิน

1. อาจารย์ที่ได้รับมอบหมาย หรือเจ้าหน้าที่ บันทึกสรุป ปัญหา ข้อเสนอแนะ และความต้องการของสถานประกอบการได้.
2. การกด complete ของนัดนิเทศทำได้เฉพาะนัด `PUBLISHED` หรือ `POSTPONED`; ต้องระบุอาจารย์ที่เข้าร่วมจริงจากรายชื่อที่ถูกกำหนดไว้.
3. ระบบตั้งนัดเป็น `COMPLETED`, บันทึกเวลาและล็อกนัด. หลังจากนี้จึงเปิดให้ประเมินได้.

## 6. ประเมิน

อาจารย์เปิดแบบประเมินจาก `/lecturer/evaluations/:id` โดยต้องเป็นอาจารย์ที่ได้รับมอบหมายให้กับนัดนั้น และนัดต้อง `COMPLETED`.

- **ประเมินนักศึกษา:** ให้คะแนน 6 ด้าน—ความรับผิดชอบ, วินัย/จริยธรรม, การสื่อสาร, ความรู้, คุณภาพงาน และแก้ปัญหา—พร้อมจุดเด่น ปัญหา ข้อเสนอแนะ และการติดตาม. บันทึกร่างได้; การส่งต้องมีคะแนนครบทุกด้าน
- **ประเมินสถานประกอบการ:** ให้คะแนน 13 ด้านครอบคลุมงาน การสนับสนุน สภาพแวดล้อม ความปลอดภัย สวัสดิการ/การเดินทาง และการประสานงาน พร้อมข้อสังเกตและคำแนะนำ
- การส่งผลเปลี่ยน evaluation เป็น `SUBMITTED`, บันทึกเวลา, ล็อกการแก้ไขของผู้ประเมินคนนั้น และแจ้งเจ้าหน้าที่
- เจ้าหน้าที่เข้าดูผลรวมและ export ได้ที่ `/staff/evaluations`; lecturer เห็น draft ของตนเองและผลที่ส่งแล้วตามสิทธิ์

## กฎสำคัญและจุดที่ต้องระวัง

- ต้องแยก `StudentApplication` (การสมัคร/การตอบรับบริษัท) ออกจาก `PlacementRequest` (คำร้องและเอกสาร). การยืนยันเลือกบริษัทจึงไม่ใช่การยืนยันเอกสารขั้นสุดท้าย
- การเปลี่ยนสถานะและการสร้างข้อมูลสำคัญทำบน server พร้อม session/RBAC และหลายจุดใช้ transaction
- คำร้องที่ยืนยันแล้วคือแหล่งข้อมูลสำหรับกลุ่มและนัดนิเทศ; อย่าใช้รายการสมัครที่ยังไม่ confirmed เป็นข้อมูลนิเทศ
- ผลประเมินต้องรอให้นัดนิเทศ completed และผลที่ submitted แก้ไขไม่ได้ตาม API ปัจจุบัน
- ไฟล์เอกสารเก็บผ่าน file storage ตาม `FILE_STORAGE_ROOT`; production ต้องกำหนด session password และ database URL ที่ปลอดภัย

## สิ่งที่ยังต้องยืนยันก่อนใช้เป็นระเบียบปฏิบัติจริง

- ผู้มีสิทธิ์เป็นคนอัปเดตสถานะการตอบรับของบริษัทในแต่ละช่วง (API อนุญาต student/staff ตาม transition แต่ UI/กระบวนการธุรกิจอาจกำหนดละเอียดกว่านั้น)
- การอนุมัติรอบสหกิจ, deadline ของเอกสาร และเกณฑ์ว่าต้องนิเทศกี่ครั้ง
- การประเมินที่ส่งแล้วควรมีขั้นตอนแก้ไข/ถอนส่งหรือไม่ และใครอนุมัติ
- การแจ้งเตือนภายนอก เช่น email/SMS และการเชื่อม SSO/LDAP ไม่ได้อยู่ใน flow ที่ตรวจพบ
