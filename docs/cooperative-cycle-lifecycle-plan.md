# แนวคิดและ Flow ของรอบสหกิจศึกษา

> เอกสารนี้อธิบายแนวคิดของ `CooperativeCycle` สำหรับให้ agent ออกแบบหน้าและ API ฝั่งเจ้าหน้าที่
> ทุก feature ที่เป็นงานรายรอบต้องอ่านเอกสารนี้ก่อนเริ่มทำ

## แนวคิดหลัก

รอบสหกิจคือ **context หลักของงานเจ้าหน้าที่** ไม่ใช่เพียงข้อมูลวันเปิด–ปิดรับสมัคร

เจ้าหน้าที่สร้างรอบหนึ่งครั้งสำหรับภาคเรียน/ปีการศึกษาหนึ่ง แล้วเลือกเข้าสู่รอบนั้นก่อนทำงาน
เช่น รอบ `2/2569 · รุ่น 2566` จากนั้นทุกหน้าที่อยู่ใต้รอบจะแสดงและจัดการเฉพาะข้อมูลของ
รอบที่เลือกเท่านั้น

```text
รายการรอบสหกิจ
  → เจ้าหน้าที่เลือกรอบ 2/2569
  → เข้า workspace /staff/cooperative-cycles/:cycleId
  → ทุกเมนูย่อย query/filter ด้วย cycleId เดียวกัน
```

ไม่ต้องมีสถานะ “ร่าง” รอบถูกสร้างแล้วใช้งานตามสถานะปัจจุบันของระบบได้ทันที

## ข้อมูลที่เจ้าหน้าที่สร้างสำหรับหนึ่งรอบ

เมื่อสร้างรอบ เจ้าหน้าที่กำหนด:

- ภาคเรียน
- ปีการศึกษา
- รุ่นนักศึกษา
- วันเปิด–ปิดรับสมัคร/คำร้อง
- วันเริ่ม–สิ้นสุดฝึกงาน
- สถานะรอบ
- หมายเหตุ (ถ้ามี)

กติกาขั้นต่ำ:

- ภาคเรียนและปีการศึกษาห้ามซ้ำ
- วันเปิดรับต้องไม่เกินวันปิดรับ
- วันปิดรับต้องไม่เกินวันเริ่มฝึก
- วันเริ่มฝึกต้องไม่เกินวันสิ้นสุดฝึก
- รอบที่ปิดแล้วแก้ไขหรือเพิ่มข้อมูลผ่าน flow ปกติไม่ได้

ข้อมูลเหล่านี้เป็นข้อมูลกลางของรอบ จึงต้องแสดงใน header ของทุกหน้าภายในรอบเสมอ

## สถานะของรอบ

ใช้สถานะที่มีอยู่แล้ว 4 ค่า:

| ค่า | ข้อความ | ความหมาย |
| --- | --- | --- |
| `OPEN_FOR_APPLICATION` | เปิดรับคำร้อง | นักศึกษารุ่นที่กำหนดสมัครและส่งข้อมูลได้ |
| `APPLICATION_CLOSED` | ปิดรับคำร้อง | ไม่รับการสมัครใหม่; เจ้าหน้าที่ดำเนินการคำร้อง/เอกสารต่อ |
| `IN_PROGRESS` | กำลังฝึกงาน | สถานที่ฝึกได้รับการจัดการแล้ว; ทำงานนิเทศและติดตามผล |
| `CLOSED` | ปิดรอบ | ข้อมูลเป็นประวัติแบบอ่านอย่างเดียว |

Flow ปกติ:

```text
เปิดรับคำร้อง → ปิดรับคำร้อง → กำลังฝึกงาน → ปิดรอบ
```

การเปลี่ยนสถานะเป็น action ที่เจ้าหน้าที่กดยืนยัน ไม่ให้แก้ค่า status อิสระจาก form ทั่วไป
ก่อนปิดรอบ ให้แสดงงานค้าง เช่น คำร้อง, เอกสาร, ตารางนิเทศ หรือการประเมิน เพื่อให้เจ้าหน้าที่
ตัดสินใจได้ครบถ้วน

## โครงสร้าง UI ใต้รอบ

Route หลัก:

```text
/staff/cooperative-cycles
/staff/cooperative-cycles/:cycleId
```

เมื่อเข้า `/staff/cooperative-cycles/:cycleId` ให้ถือ `cycleId` ใน URL เป็น source of truth
สำหรับ context ปัจจุบัน ไม่ใช้ “รอบล่าสุด” หรือค่าจาก browser storage แทน

ทุกหน้าลูกอยู่ใต้ route เดียวกัน:

```text
/staff/cooperative-cycles/:cycleId              ภาพรวมรอบ
/staff/cooperative-cycles/:cycleId/students     รายชื่อนักศึกษาในรอบ
/staff/cooperative-cycles/:cycleId/applications คำร้อง/การสมัคร
/staff/cooperative-cycles/:cycleId/placements   สถานที่ฝึกงานที่ยืนยัน
/staff/cooperative-cycles/:cycleId/supervisors  การจัดอาจารย์นิเทศ
/staff/cooperative-cycles/:cycleId/visits       ตารางนิเทศ
/staff/cooperative-cycles/:cycleId/evaluations  การประเมิน
/staff/cooperative-cycles/:cycleId/budgets      งบประมาณ
/staff/cooperative-cycles/:cycleId/documents    เอกสาร
```

### Context header

ทุกหน้าลูกต้องเห็นข้อมูลของรอบที่กำลังเลือกอย่างน้อย:

```text
ภาคเรียนที่ 2/2569 · รุ่น 2566     [เปิดรับคำร้อง]
ช่วงรับคำร้อง: 1 ก.ค. – 31 ส.ค.    ช่วงฝึกงาน: 1 พ.ย. – 28 ก.พ.
```

header ต้องมี:

- breadcrumb กลับหน้ารายการรอบ
- cycle switcher เพื่อเปลี่ยนไปอีกรอบ
- เมื่อเปลี่ยนรอบ ให้พยายามเปิดโมดูลเดิมของรอบใหม่ เช่น `visits` ของรอบใหม่; หากไม่มี route
  นั้น ให้กลับไป overview ของรอบใหม่
- `CLOSED` แสดง read-only alert และซ่อน action แก้ไข/เพิ่มข้อมูล

## Logic การแสดงข้อมูลตามรอบที่เลือก

ทุก API และ query ต้องรับ `cycleId` จาก path และบังคับ filter ด้วย ID นี้ใน server เสมอ

ตัวอย่าง:

| หน้าจอ | ข้อมูลที่แสดง | เงื่อนไขหลัก |
| --- | --- | --- |
| ภาพรวมรอบ | จำนวน/งานค้างของคำร้อง, placement, teacher, visit, evaluation, budget | query เฉพาะ `cycleId` |
| นักศึกษา | นักศึกษารุ่น/ผู้เข้าร่วมรอบนั้น | membership หรือ cohort ของรอบ |
| คำร้อง | application/request ของนักศึกษาในรอบ | `application.cooperativeCycleId = cycleId` |
| สถานที่ฝึกงาน | placement ที่ยืนยันในรอบ | placement/request อยู่ใน cycle เดียวกัน |
| อาจารย์นิเทศ | กลุ่มและอาจารย์ที่มอบหมายในรอบ | supervision group อยู่ใน cycle เดียวกัน |
| ตารางนิเทศ | visit ที่กำหนดในรอบ | `visit.cooperativeCycleId = cycleId` |
| การประเมิน/งบประมาณ/เอกสาร | record ที่เกิดจากงานรอบนั้น | relation กลับมาที่ cycle เดียวกัน |

ห้ามใช้เพียง filter ใน frontend เพราะ user สามารถเรียก API ข้ามรอบเองได้ API mutation ต้อง
ตรวจด้วยว่า record ที่แก้ไขเป็นของ `cycleId` จาก URL ก่อนทำงาน

## การไหลของงานใต้รอบ

```text
1. Staff สร้างรอบและกำหนดเวลา/รุ่น
2. รอบเปิดรับ → นักศึกษาของรุ่นนั้นสมัครสถานประกอบการ
3. Staff ปิดรับ → ตรวจคำร้อง/ออกหนังสือ/ตรวจเอกสาร
4. ยืนยันสถานที่ฝึก → ข้อมูลไปอยู่ในเมนูสถานที่ฝึกงานของรอบ
5. จัดอาจารย์และกลุ่มนิเทศ → สร้างตารางนิเทศของรอบ
6. ระหว่างฝึก → ติดตามตาราง, การประเมิน และงบประมาณ
7. ปิดรอบ → เก็บทุกอย่างเป็นประวัติ read-only
```

ดังนั้น UI ไม่ควรวาง “คำร้อง”, “ตารางนิเทศ” หรือ “งบประมาณ” เป็นข้อมูลรวมทุกปีในหน้าเดียว
แต่ต้องเข้าผ่าน cycle workspace ก่อนเสมอ

## ภาพรวมรอบต้องแสดงอะไร

หน้า `/staff/cooperative-cycles/:cycleId` เป็นหน้าตอบคำถามว่า “รอบนี้ทำถึงไหนแล้ว”:

- จำนวนนักศึกษาของรอบ
- คำร้องที่รอดำเนินการ
- สถานที่ฝึกงานที่ยืนยันแล้ว/ยังค้าง
- นักศึกษาที่ยังไม่มีอาจารย์นิเทศ
- ตารางนิเทศที่ยังไม่กำหนดหรือยังไม่เผยแพร่
- การประเมินและงบประมาณที่ค้าง

ตัวเลขทุกตัวต้องกดไปยังหน้าลูกพร้อม filter ของรอบนั้นได้ ไม่แสดงตัวเลข placeholder

## กฎการป้องกันข้อมูลข้ามรอบ

- record ลูกทุกชนิดต้องเชื่อมกลับมาที่ cycle ได้โดยตรงหรือผ่าน relation ที่ตรวจสอบได้
- ห้ามนำ application/request/placement/visit ของรอบ A ไปแก้จาก URL ของรอบ B
- ปุ่ม create ทุกหน้าต้องสร้าง record ผูก `cycleId` ที่เลือกอยู่ ไม่ให้ client ส่ง cycle ID อื่น
- เมื่อปิดรอบ server ปฏิเสธ mutation ปกติทั้งหมดของรอบนั้น
- ลบรอบได้เฉพาะเมื่อไม่มีข้อมูลลูกที่อ้างอิง; หากมีข้อมูลแล้วให้ปิดรอบแทน

## ลำดับทำงานสำหรับ agent

1. ทำ cycle list และ create/edit ตามข้อมูลพื้นฐาน
2. ทำ workspace shell ที่อ่าน `:cycleId`, context header และ cycle switcher
3. ย้าย/สร้างหน้าลูกทั้งหมดใต้ `:cycleId`
4. ปรับ API ทุกชุดให้ filter และ validate ด้วย `cycleId`
5. ทำ overview จากข้อมูลจริงของแต่ละโมดูล
6. เพิ่ม guard ตาม status รอบ และ read-only เมื่อ `CLOSED`

## เกณฑ์ตรวจรับ

- เจ้าหน้าที่เลือก cycle แล้วเห็นชื่อรุ่น ช่วงเวลา และสถานะถูกต้องทุกหน้าลูก
- เปลี่ยน cycle แล้วข้อมูลคำร้อง/สถานที่/นิเทศ/งบประมาณเปลี่ยนตาม cycle ที่เลือก
- refresh หรือเปิด URL โดยตรงยังอยู่ใน cycle เดิม
- API ปฏิเสธ record ที่ไม่ได้อยู่ใน `cycleId` ของ request
- `CLOSED` แก้หรือเพิ่มข้อมูลผ่าน UI/API ปกติไม่ได้
- ไม่มีหน้ารวมข้อมูลหลายรอบที่ทำให้เจ้าหน้าที่สับสนว่ากำลังจัดการรอบใด
